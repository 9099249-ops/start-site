# Работа с изменениями СТАРТа

Основная ветка: `main`. Репозиторий: `9099249-ops/start-site`.
Существенные изменения выполняются только в отдельной ветке и поступают в main
через Pull Request после независимого review и решения владельца.

## Перед началом

1. Прочитать применимые AGENTS.md, README и инструкции предметной области.
2. Проверить `git status`, текущую ветку, remote и установленные hooks.
3. Выполнить `git fetch origin`. Чистую main обновлять только `git pull --ff-only`.
4. Если checkout грязный, не переключать/сбрасывать его и не коммитить чужую работу.
   Создать отдельный checkout от origin/main либо согласовать принадлежность правок.
5. Создать ветку с конкретным названием: `fix/order-printing`,
   `feature/cafe-inventory`, `ui/admin-cleanup`, `docs/code-review-workflow`.

## Реализация и проверки

Минимальный diff, существующие API и библиотеки. Не выполнять несвязанные правки.
Только отдельные тестовые базы и фиктивные интеграции; никакой production-проверки
реальным заказом, платежом, изменением остатков или повторной печатью.

Команды из корня проекта:

```sh
node --test --test-concurrency=4 server/*.test.mjs
python -m unittest discover -s start-print-agent -p "test*.py"
```

Для игры из `game-src/`:

```sh
npm ci
npm test
npm run build
```

Серверу и обычному сайту не нужны npm install или сборка. Отдельных команд lint
нет. Typecheck игры встроен в build (`tsc --noEmit`); у сервера отдельного
typecheck нет. Не отмечать отсутствующую проверку как пройденную: писать
«не предусмотрена». Для изменения UI проверить телефон и desktop; при отсутствии
браузерной проверки честно описать ограничение.

Сверить `git diff` и staged diff, не использовать бездумно `git add -A` в общем
грязном checkout. Не включать .env, базы, пароли, закрытые ключи, архивы и клиентские данные.
Сбой, воспроизводимый до изменений, отдельно записать в PR; не выключать тест.

## Commit, push, PR

1. Создать осмысленный commit только файлов задачи.
2. `git push -u origin <ветка-задачи>`.
3. Создать PR в main по `.github/pull_request_template.md`.
4. Прикрепить ссылку к задаче Codex и запросить отдельный code review.
5. Если репозиторий подключён к Code Review, написать `@codex review` в PR.
6. Исправить замечания, повторить проверки и обновить PR. Новый commit делает
   прежнее review потенциально устаревшим; нужна проверка последнего diff.
7. Не выполнять merge и не включать auto-merge. Владелец решает после review
   и успешных проверок. Отсутствие замечаний бота не заменяет решение человека.

Очень мелкое изменение без PR возможно только с явным разрешением владельца
и не отменяет запрет обхода защиты веток.

## Локальная защита

В этом PR находятся `.githooks/pre-commit` и `.githooks/pre-push`.
Для нового checkout включить их из корня:

```sh
git config --local core.hooksPath .githooks
```

Перед этим проверить старое значение `git config --get core.hooksPath` и custom
hooks: существующую систему не заменять без согласования. Hooks запрещают commit
и прямой push в main, а pre-commit также проверяет опасные имена staged файлов.
Единственное исключение для `.pem` — `firmware/esp32-bms-gateway/releases/public-key.pem`,
если файл начинается с `BEGIN PUBLIC KEY` и не содержит блока закрытого ключа.
Это локальная страховка, не защита GitHub и не полноценный сканер секретов.
Агент не использует `--no-verify` или подмену hooksPath для обхода.

## Публикация

CI не публикует сайт и не использует production-секреты. Merge и выпуск — разные
операции. Сервер, база, env и Raspberry Pi изменяются только по отдельному
разрешению на конкретный выпуск согласно существующим инструкциям `deploy/`.

Настройка GitHub, ограничения и рекомендуемая защита main:
[`docs/code-review-workflow.md`](docs/code-review-workflow.md).
