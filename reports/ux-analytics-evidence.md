# UX-аудит: доступные данные и план измерений

Дата исследования: 2026-10-05. Основание: только исходники этого checkout и инструкции репозитория. Production не открывался; никакие production-данные и внешние сервисы не использовались. Отчёт описывает возможность будущего наблюдения, а не результаты наблюдения.

## Краткий вывод

- Уже доступны доменные следы операций: журнал действий персонала/финансов, события заказов кафе, история бронирований и транзакционные таблицы. Это не телеметрия UI.
- Клиентского UX-сборщика в `dist/admin/performance.js` нет: он оборачивает `fetch`, дедуплицирует GET и показывает статус записи, не отправляя клики, переходы, длительности или содержимое формы ([performance.js](../dist/admin/performance.js):2-18).
- Для админки не обнаружен централизованный UX-сбор кликов/просмотров, Web Vitals или session replay. На публичном сайте уже есть Яндекс Метрика: `dist/analytics.js:2-13` разрешает ограниченные публичные URL и цели, исключает `/admin/`, отключает webvisor/clickmap. Общий движок кафе вызывает `window.startAnalytics`, но это не подтверждает сбор внутри админки. Нельзя восстановить фактическую последовательность кликов сотрудников по имеющимся доменным данным.
- Предложенный сбор на 72 часа ниже — план, не включён и не расписан. Реальных 72-часовых результатов нет.

## Что отсутствует и что можно вывести

В административном интерфейсе не найден полноценный сбор UX-сценариев; `performance.js` даёт локальную обратную связь при сетевой записи. Публичная Яндекс Метрика в `dist/analytics.js` не должна автоматически расширяться на админку: там другая чувствительность данных. Состояние внешних счётчиков и инфраструктуры этим аудитом не проверялось.

По текущим следам можно посчитать некоторые оформленные заказы, завершённые оплаты, возвраты, смены и аудитируемые изменения. В пределах доступных полей иногда можно связать действие с аккаунтом сотрудника и временем. Нельзя достоверно посчитать:

- какие экраны сотрудник открывал без последующего действия, куда нажимал, что искал, в каком порядке проходил сценарий;
- число повторных попыток, неотправленных форм, отказов до API и брошенных задач;
- сколько UI-времени ушло на действие и было ли ожидание связано с сетью, устройством или сложностью интерфейса;
- личность оператора для каждой записи там, где событие её не хранит, либо намерение за пределами зафиксированного бизнес-результата.

Статус операции не равен клику: один результат может следовать из нескольких попыток, а клик не обязан приводить к записи в БД. Нельзя делать персональные выводы о продуктивности сотрудников по неполным доменным логам.

## Приватность и границы сбора

- Не собирать URL целиком: query-параметры могут нести поиск, идентификаторы, дату или состояние экрана; фрагменты URL могут отражать выбранную запись. Передавать только allowlist `page_id`/`view_id`, без query, hash, имени клиента, телефона, rental/order ID.
- Не отправлять текст кнопки/ARIA-label, текст DOM, значение поля, введённый поиск, reason/comment, URL изображения или payload запроса. Метки UI и значения форм могут включать ФИО, телефон, сумму, причину, расписание или другие данные сотрудников/клиентов. Событие должно ссылаться на стабильный код действия из allowlist.
- Не включать session replay/запись экрана/DOM: такие технологии могут захватить видимые формы, записи клиентов, суммы, смены, тосты ошибок и динамически вставленный контент. Маскирование полей снижает, но не устраняет риск; replay не нужен для предложенной задачи.
- Не сохранять IP, cookie, session token, login, employee ID, device fingerprint или cross-session ID в UX-событии. Пользовательский аккаунт уже нужен приложению для авторизации; аналитика не должна создавать второй персональный профиль.
- Использовать случайный псевдоним только для одной вкладки/сессии через `sessionStorage`, обновлять после 30 минут бездействия и при новой сессии; очищать при выходе. Никакой серверной таблицы соответствия с аккаунтом. Этот ID всё равно является псевдонимным идентификатором, поэтому ограничить доступ и срок хранения.
- Период сбора ограничить 72 часами; определить владельца доступа, удаление сырых событий (например, через 7 дней) и передачу только агрегатов. Точный срок, уведомление сотрудников и правовое основание согласовать до включения, не считать этот отчёт юридической оценкой.

## Предлагаемый allowlist для кафе и проката

Ниже проект будущего контракта, не существующие события и не кодовая реализация. Собирать только изменение состояния страницы/пользовательское действие, а не фоновые polling-запросы.

| Область | События-коды (пример) | Безопасные атрибуты |
|---|---|---|
| Общая навигация | `page_open`, `nav_select`, `search_submit`, `search_clear` | `page_id` из enum (`rental`, `cafe`, `purchase`, `tasks`, `settings`, `workforce`, `schedule`); `control_id` из enum; `source_page_id` |
| Кафе | `cafe_order_list_filter`, `cafe_order_open`, `cafe_order_status_action`, `cafe_item_edit_open`, `cafe_order_submit_result` | enum фильтра/статуса/типа операции; `result` из `success/failure/cancel`; длительность в диапазоне; не order ID, товарное имя или текст ошибки |
| Прокат | `rental_view_select`, `rental_search_submit`, `rental_booking_open`, `rental_issue_open`, `rental_issue_submit_result`, `rental_return_action` | enum панели/типа операции/результата; диапазон длительности; не клиент, техника конкретного клиента, телефон, сумма или rental ID |
| Сессия | случайный `session_id` на вкладку; `event_id` для дедупликации; относительное время от начала сессии | `schema_version`, allowlisted `page_id`, `event_name`, безопасные enum-поля, округлённая длительность, грубая категория устройства (mobile/desktop) при необходимости |

Для ошибок отправлять только allowlisted класс (`network`, `validation`, `server`, `conflict`) и HTTP-класс статуса, без текста ответа/стека. Не считать каждый `click`: регистрировать ограниченный набор целевых действий, чтобы не превращать поток в поведенческое наблюдение.

## План отчёта за 72 часа на существующей инфраструктуре

Инфраструктура приложения уже использует встроенный Node HTTP и SQLite (`README.md:17-18`), но UX-таблицы/endpoint сейчас нет. Предлагаемый путь после отдельного согласования: добавить отдельную таблицу локальной SQLite для allowlisted UX-событий и минимальный same-origin endpoint с валидацией enum, лимитом размера, защитой Origin/авторизацией и очисткой по TTL; агрегировать её запросами Node/SQLite и выгружать сводку как локальный Markdown/CSV. Не переиспользовать `financial_audit_log`, `cafe_order_events` или `admin_audit`: их назначение/retention и поля бизнес-критичны, а аналитика смешала бы разные цели.

Отчётные срезы на 72-часовом окне: открытия разделов и переходы между ними; число целевых действий по области/сценарию; доля успеха/ошибки/отмены на allowlisted submit; медиана и p90 времени между открытием сценария и результатом; частые переходы назад/повторы только при наличии безопасного кода события; разделение по грубой категории устройства. Для маленькой выборки показывать абсолютное `n`, не ранжировать сотрудников и не выводить сегменты с малым числом сессий. Сопоставить агрегаты с бизнес-журналами только на уровне времени и общих количеств, без склейки с конкретным оператором/заказом.

Операционный план, без включения сейчас: утвердить список событий и уведомление; реализовать и проверить в локальной фиктивной базе; отдельно определить дату/время старта и автоостановки через существующий локальный механизм запуска/таймер приложения либо ручное отключение; проверить поступление только синтетических записей; после согласования собирать 72 часа; отключить сбор, агрегировать, удалить сырые события согласно утверждённому сроку и выдать сводку. В репозитории не найден настроенный сборщик/расписание UX-отчётов; автоматическая production-публикация не настроена (`README.md:67-69`). Поэтому сейчас ничего не включалось и не планировалось.

## Навигация и гипотезы о малоиспользуемых функциях

Основная верхняя навигация строится в `dist/admin/ops-nav.js:5-9`: **Прокат**, **Кафе**, **Закупка**, **Дела**, **Настройки**. Для прокатного рабочего стола отдельные панели **На воде**, **Брони**, **За день**, **Клиенты**, **Ещё** находятся в `dist/admin/index.html:12`; в «Ещё» также доступны отчёт/операционные инструменты и редактор сайта (та же страница, секции ниже). График и смены/зарплата имеют отдельные страницы: `dist/admin/workforce.html:1-3`, `dist/admin/schedule.html:1-2`. Настройки группируют личную работу и администраторские разделы; `dist/admin/settings.js:22` формирует видимые ссылки по роли.

Кандидаты для проверки, но **не вывод об их низком использовании**: функции, спрятанные под «Ещё», редактор сайта/SEO внутри прокатного экрана, отдельные настройки аккаунтов, aQsi, печать, возвраты, график, чек-листы и складские формы. Код подтверждает существование интерфейса и точки входа, но не показывает частоту использования. Проверять эти гипотезы можно только агрегированным `page_open`/целевыми событиями после согласованного сбора; нельзя объявлять функцию неиспользуемой на основании отсутствия строк в бизнес-журнале.

## Изолированный запуск и проверки

Для полного локального сайта без БД админские функции отключены (`README.md:19-25`). Для демонстрации админки с временной SQLite и подменёнными исходящими SMS/Telegram предусмотрен:

```powershell
node server/sms-demo.mjs
```

Скрипт задаёт временную БД, адрес loopback `127.0.0.1:14876` и фиктивные credentials интеграций (`server/sms-demo.mjs:1-12`); локальные учётные данные demo печатаются самим скриптом. Не добавлять `.env`, production `BOOKING_DB`, реальные SMS/Telegram/AQSI secrets. Запустить из корня проекта по Node.js 24; затем открыть адрес, указанный скриптом. Для простого публичного сайта без админки: `node server/server.mjs`, без `BOOKING_DB` (`README.md:19-25`).

Полезные изолированные проверки из корня:

```powershell
node --test server/*.test.mjs
node --test server/cafe-compose-ui.test.mjs server/aqsi-cafe.test.mjs server/cafe-board.test.mjs
node --test server/rental-ui.test.mjs server/rental-pricing.test.mjs server/guest-rental-route-ui.test.mjs
```

Первые две команды документированы в `README.md:57-65` и `server/AGENTS.md:37-45`; третья подбирает имеющиеся тесты проката, без запуска боевой базы. Дополнительные изолированные визуальные previews табло кафе: `node server/testing/cafe-board-preview.mjs` (порт 4187) и redesign preview `node server/testing/cafe-board-redesign-preview.mjs` (порт 4195); они отдают фиктивные данные и не являются полной демо-админкой (`server/testing/cafe-board-preview.mjs:4`, `server/testing/cafe-board-redesign-preview.mjs:3-4`).
