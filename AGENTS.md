# СТАРТ: руководство агентами

Главный агент (GPT-6, наиболее сильная доступная модель) руководит задачей: понимает запрос целиком, определяет архитектуру, распределяет работу и отвечает за финальный результат.

```text
Use the strongest model to think.
Use Luna to find and understand.
Use Luna to implement scoped changes.
Use the strongest model to review.
```

## Область действия и существующие инструкции

- Этот файл действует на весь репозиторий. Локальные `AGENTS.md` дополняют его для соответствующих папок; перед работой прочитать всю применимую цепочку.
- Прямые инструкции пользователя имеют приоритет. Для запуска, сборки, окружения, инфраструктуры и конкретных команд сохранять приоритет существующих README и специальных инструкций проекта. Не заменять их придуманными командами.
- `README.md`, `server/README.md`, `start-print-agent/README.md`, `game-src/README.md` и документы в `deploy/` сохраняются. Датированные отчёты и документы с названием DRAFT описывают историю, а не подтверждают состояние текущего checkout или сервера. При противоречии с кодом сообщить главному агенту и проверить актуальный источник.
- Эти файлы задают порядок работы, а не автоматически переключают модели. Использовать реальные инструменты делегирования и доступные в них идентификаторы моделей. Не изменять настройки приложения или аккаунта ради выполнения этих инструкций.

## Распределение работы

### GPT-6: руководитель, архитектор и финальный ревьюер

Использовать для понимания задачи целиком, планирования, архитектуры, сложной бизнес-логики, БД и миграций, API-контрактов, авторизации и безопасности, бронирования, платежей, зарплаты, изменений нескольких модулей, разрешения неоднозначностей, финального code review и итоговой проверки результата.

Перед глобальным поиском, поиском файла/строки, массовым чтением кода, обычной CSS-правкой, заменой текста или механической реализацией готового плана главный агент спрашивает себя:

> Can this safely be delegated to Luna?

Если да, делегировать. Не повторять уже порученное исследование; читать отчёт и необходимые для архитектуры или review участки. Главный агент интегрирует изменения и проверяет их сам.

### Luna: поиск, понимание и независимая проверка

Использовать модель `gpt-6-luna`. В исследовательской роли работать read-only; исполнительская роль описана ниже. Независимую проверку значимого изменения поручать отдельному агенту Luna, который не реализовывал это изменение, а не самопроверке исполнителя.

По умолчанию работает read-only. Искать файлы, функции, компоненты и строки; трассировать данные; находить API, все места использования поля, зависимости и тесты; читать текущую реализацию; сравнивать похожие решения; искать побочные эффекты. При проверке diff изучать также связанные места, а не только строки изменения. Исследование рискованного модуля допустимо без изменения его поведения.

Компактный отчёт, с путями и строками там, где они помогают:

1. Relevant files
2. Relevant functions/components
3. Current behavior
4. Dependencies
5. Possible side effects
6. Existing tests
7. Risks/questions

Не копировать большие файлы в отчёт. Отделять наблюдения из кода от предположений и исторических сведений.

### Luna: исполнитель ограниченного плана

Использовать `gpt-6-luna` для локальных изменений кода, UI, CSS, компонентов и форм, простых API-реализаций по уже согласованному контракту, багфиксов, валидации, тестов, небольшого рефакторинга и механических изменений. Luna не принимает самостоятельных архитектурных решений.

Уровень размышлений `low` для поиска, подписей, CSS и механических правок; `medium` для небольших багфиксов, тестов и независимой проверки по чёткому плану. Не выбирать автоматически GPT-6.1 Sol для обычной реализации. При усложнении задачи возвращать её главному агенту.

Экономить контекст: давать агенту конкретный вопрос, пути и критерии, не копировать всю историю или большие файлы; не повторять уже выполненный поиск. Закрывать завершённых агентов, когда они больше не нужны. Не запускать отдельного проверяющего для очевидной подписи или CSS, если достаточно финальной проверки главного агента.

Поручение должно содержать цель, точный scope и допустимые файлы, согласованное поведение/контракт, неизменяемые условия, критерии приёмки и подходящие проверки. Не поручать двум исполнителям пересекающиеся изменения одних файлов; учитывать уже существующие незакоммиченные изменения. Выход за scope возвращается главному агенту.

Отчёт исполнителя:

1. Files changed
2. What changed
3. Tests/checks run
4. What could not be verified
5. New risks discovered

Если Luna недоступна в текущем инструменте, кратко сообщить об этом. Не называть другую модель её именем и не утверждать, что делегирование состоялось. Главный агент выполняет необходимый ограниченный участок сам либо использует явно обозначенный доступный вариант; при наличии Luna сохраняет независимую проверку. Ограничение инструмента не является причиной бросать разрешённую задачу или создавать отдельный пользовательский чат.

## Эскалация

Luna в любой роли останавливает изменение и возвращает задачу GPT-6 до принятия решения, если требуется или неожиданно обнаружено:

- изменение схемы БД или миграция;
- изменение авторизации, прав доступа или безопасности;
- изменение публичного API/контракта;
- изменение платежной или зарплатной логики;
- destructive operation или риск потери данных;
- изменение общей архитектуры либо нескольких крупных модулей;
- concurrency/race condition или изменение транзакций/идемпотентности;
- новая инфраструктура или внешний сервис;
- противоречивые бизнес-правила.

Передать факты, связанные файлы, риск и вопрос, требующий решения. Не обходить запреты, не ослаблять проверки ради зелёного теста и не расширять scope самостоятельно. GPT-6 определяет решение и берёт чувствительную часть на себя; отделённые безопасные механические части можно делегировать по новому точному поручению.

## Стандартный workflow

1. GPT-6 понимает запрос пользователя и границы разрешённой работы.
2. Luna находит код, зависимости, shared data и тесты.
3. GPT-6 анализирует отчёт Luna и разрешает неоднозначности.
4. GPT-6 составляет минимальный безопасный план и scope исполнителя.
5. Luna-исполнитель реализует ограниченное изменение и сообщает результаты проверок.
6. Отдельный агент Luna, не выполнявший реализацию, независимо проверяет diff, зависимости и связанные сценарии.
7. GPT-6 выполняет финальный code review.
8. Запускаются подходящие тесты/проверки; новые проблемы возвращаются в цикл исправления и review.
9. GPT-6 принимает результат только после проверки и сообщает фактический итог и оставшиеся ограничения.

Fast path: очевидную подпись, текст кнопки, опечатку, отступ, цвет, размер шрифта или удаление явно указанного лишнего UI-элемента можно сразу поручить Luna с уровнем `low`. Это не разрешает скрывать важные данные или менять бизнес-поведение. Даже для fast path главный агент просматривает diff и проверяет затронутый интерфейс; полный исследовательский цикл не нужен.

## Карта проекта и команды

- `server/`: HTTP/API, SQLite, бронирование, прокат, кафе, платежи, персонал, зарплата, склад, клиенты и уведомления. Доменные модули лежат вместе; точная карта и ограничения в `server/AGENTS.md`.
- `dist/`: непосредственно обслуживаемый сайт, публичное меню, клиентские статусы, табло и готовая игра; `dist/admin/`: админка и POS. Здесь не предполагать обязательную сборку сайта.
- `start-print-agent/`: Python, Raspberry Pi и CUPS; очередь и доставка печатных документов.
- `deploy/`: конфигурации и специальные инструкции существующего сервера.
- `game-src/`: исходники SUP-игры, отдельный TypeScript/Vite-проект. `dist/game/` содержит опубликованный результат, а не основное место правок игры.

Из корня репозитория, Node.js 24:

```sh
node server/server.mjs
node server/sms-demo.mjs
node --env-file=.env server/server.mjs
node --test server/*.test.mjs
```

Выбрать нужный режим, а не запускать все сразу. Обычный адрес: `http://127.0.0.1:4173/`; без `BOOKING_DB` административные функции отключены. `server/sms-demo.mjs` использует временную базу и подменённые SMS/Telegram. Для постоянной локальной базы следовать README и `.env.example`; production-базу для разработки не использовать. У сайта нет отдельной сборки и серверного `npm install`.

Из `game-src/`: `npm ci`, `npm test`, `npm run build`, `npm run dev`; подробности и требования версий в его README. Печать и production обслуживаются только по своим локальным инструкциям.

## Общие бизнес-условия

- Перед изменением shared data поручать Luna поиск всех мест использования, включая API, сохранённые данные, браузерные интерфейсы, уведомления, печать и тесты. Изменение одного поля может затронуть несколько экранов.
- Кафе: POS, кухня, публичное табло, клиентский статус, талон/чек, склад и уведомления связаны. Заказ с сайта готовят до оплаты; обычный POS-заказ с терминалом передают на кухню после оплаты. Отложенный счёт гостя и быстрая выдача имеют отдельные существующие правила.
- Ручное подтверждение уже полученных денег не запускает повторное списание или новый фискальный чек. Неизвестный результат оплаты разрешается только предусмотренной сверкой; подтверждённую оплату нельзя просто объявить неоплаченной. Ручные финансовые решения сохраняются в истории.
- Прокат: аренда связана с календарём, активными выдачами, таймером, просрочкой, мобильной админкой и карточкой клиента.
- Сотрудники: выход/уход со смены, наличные/безнал, изъятия, фиксированная часть, процент, итоговая выплата и Telegram-отчёт проверяются вместе. Любое изменение расчётов проходит через GPT-6. Служебный логин `admin` может оформлять заказы, но исключён из личных смен и заработка; это не исключение для всех аккаунтов с ролью `admin`.
- Админка остаётся компактной, быстрой, удобной для POS и телефона, с минимальным скроллом и без лишнего пустого места. Не удалять операционные данные ради оформления. Блок зарплаты сотрудников с главного экрана не убирать без прямого указания пользователя.
- Разные пиццы остаются отдельными товарами; не объединять их остатки.

## Идентификаторы заказов

Внутренний ID записи и номер заказа для клиента являются разными сущностями. Никогда не сбрасывать primary key или счётчик SQLite ради красивой нумерации. Существующий `dist/cafe-number.js` формирует `displayNumber` 001–999 из внутреннего ID; повтор отображаемого номера в новом цикле допустим, объединение заказов по этому номеру запрещено.

Поиск записи, ссылки, операции, идемпотентность, очередь печати и ключи табло используют внутренний ID. Если нужен новый public/display number, GPT-6 сначала определяет контракт и поведение при одновременном создании заказов. Не внедрять отдельный небезопасный `max(number) + 1` и не менять уже сохранённые идентификаторы.

## Изменения и проверка

- Предпочитать минимальный diff, существующие компоненты, паттерны, API и библиотеки. Избегать новых зависимостей, больших переписываний, побочного рефакторинга, дублирования и несвязанных файлов.
- Сохранить чужие изменения, README и специальные инструкции; ничего не удалять/перезаписывать без необходимости. Не включать секреты, базы, клиентские данные, журналы и резервные копии в Git или отчёты.
- Для значимого изменения заранее найти тесты, выполнить подходящий набор и проверить связанные сценарии. Расширять набор при финансовых, общих или многомодульных изменениях. Не заявлять о тесте, сборке, физической печати или публикации, которые не выполнялись.
- Использовать отдельную тестовую БД, фиктивные интеграции и доступный локальный runtime. Не менять реальные остатки и не запускать реальные платежи в проверках. Если тестов нет, выполнить доступную проверку и явно назвать её ограничения.
- Для изменений только документации проверить пути, ссылки, согласованность инструкций и сохранность существующих файлов; запуск бизнес-тестов не требуется.
- Коммит, push и production-публикация не являются автоматическим завершением любой задачи. Выполнять их только в разрешённом пользователем scope. Уже полученное разрешение на конкретное действие учитывать, не запрашивать повторно.
