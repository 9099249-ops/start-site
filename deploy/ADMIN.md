# Station admin, 21 September 2026

Live entry: https://spotsup.ru/admin/. Initial setup pending owner passwords. One-time setup link is local C:/Users/sacha21/.ssh/start-admin-setup.md; never commit or disclose it. Server stores only its hash. It is deleted after both accounts are created; setup cannot run again once users exist. Logins admin (administrator) and station (staff). Passwords are scrypt salted hashes. Cookies are Secure, HttpOnly, SameSite=Strict, 12-hour sessions. Administrator can reset staff password and revoke their sessions. API checks roles, authentication and exact origin. Persistent login throttling: 8 attempts/IP/15 minutes; setup 5.

Both roles can issue/return rentals, view clients, active equipment and daily collection. Each issue records category, quantity, Moscow departure datetime, name, phone, amount in integer kopecks, payment method and issuing user. Issuance saves payment and rental in one transaction. Return records actor/time, restores availability and never changes money. Idempotent issue UUID and return endpoint prevent double entries. Available stock is checked in a SQLite write transaction, including concurrent clients. Daily collection follows payment-entry date in Moscow, independent of return date. Zero amounts support season pass usage. Equipment tracked by category, not individual numbered boards. Deposits, additional payments, refunds, future reservations and incoming website-request inbox are not yet implemented. UI describes money as rental collection excluding refundable deposits. New departure must be within previous 24 hours, with five-minute clock tolerance. No test rentals exist in production.

Database is existing /var/lib/start-site/bookings.sqlite, private to service user; new tables admin_users, admin_sessions, admin_attempts, admin_config, rentals, payments, admin_audit. Now stores actual customer data for staff-entered rentals. No personal data is logged. Frontend uses textContent for customer fields. Admin responses no-store; CSP self-only scripts/styles, frame-ancestors none, X-Frame-Options DENY. Server binds loopback, Nginx overwrites client-IP header.

New validated public requests are persisted before Telegram notification in inquiries. Existing Telegram-only history cannot be imported from receipt hashes. Both roles can view paginated new/confirmed/cancelled/issued requests, confirm after client contact, cancel, and prefill an issuance. Status changes are audited in inquiry_events.
