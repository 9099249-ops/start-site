# СТАРТ: согласованный обмен заданиями печати

Статус: **согласовано владельцем и установлено 25.09.2026**. Связь сайта с Pi
проверена; физическая печать отключена до подключения принтера. Подробности — PRINT-INTEGRATION.md.

Основание: `START-PRINT-REQUIREMENTS.md`, `start-print-agent/README.md`,
`start-print-agent/main.py`, `start-print-agent/tests.py`, текущие `server/cafe.mjs`,
`server/admin.mjs`, `server/workforce.mjs` и интерфейс смен.

## Исходное состояние перед интеграцией

- Raspberry Pi: локальный API `127.0.0.1:8765`, Python/CUPS, постоянная SQLite-очередь.
- Документы `cafe_order` и `shift_report`; уникальность `(type, order_id/report_id)`.
- Повтор приёма одинакового документа не создаёт новое задание. Изменённый документ с прежним ID отклоняется.
- Задание CUPS сначала удерживается; его ID и фаза передачи сохраняются перед разрешением печати.
- Незавершённые/неопределённые попытки не должны автоматически создавать второй чек.
- Подготовлен исходящий HTTPS polling, но нет подтверждений приёма и отправки статусов сайту.
- Ручной `reprint` сейчас не имеет постоянного ID команды: его требуется дополнить для безопасного сетевого повтора.
- По документации оборудование ещё не готово к физической проверке: принтер не доставлен, `printing_enabled=false`.

## 1. Направление соединения и авторизация

Pi сам подключается к `https://spotsup.ru/api/print-agent/v1/…` примерно раз в 15 секунд.
При сетевых ошибках задержка растёт до 60 секунд; при восстановлении работа продолжается.
Входящие порты Pi и роутера не открываются; адрес `192.168.1.121` не меняется.
Браузер сотрудника работает только с сервером сайта, а не с локальным API Pi.

Отдельный Bearer-токен разрешает только задания и статусы одной назначенной очереди.
Каждый запрос передаёт `Authorization: Bearer …`, `X-Print-Agent-Id` и
`X-Print-Database-Id`. Последние два значения сверяются с серверной конфигурацией.
Это не пароль администратора и не локальный `api_token` агента. Секрет хранится только
в конфигурации сервера и защищённом конфиге Pi; не попадает в браузер, GitHub и логи.
TLS проверяется, HTTP-перенаправления запрещены, URL подтверждений не берутся из заданий.
Ответы: `Cache-Control: no-store`. Авторизация обязательна для каждого запроса.

Очередь привязана к одному устройству и постоянному идентификатору его локальной БД.
Переустановка/потеря БД или смена устройства требует ручной сверки: автоматически
отправлять все старые задания в пустую очередь нового агента нельзя.

## 2. Серверная очередь и получение

Новая очередь печати хранится в существующей SQLite сайта рядом с заказами/сменами.
Она не заменяет Telegram-очереди, платежи или начисления.

`GET /api/print-agent/v1/jobs` возвращает ограниченную пачку неизменяемых документов
и команд для назначенного агента. Обычный GET ничего не удаляет и не считает доставленным.
Повторные GET до подтверждения возвращают те же ID и тот же снимок.

Пример оболочки, поддерживаемой адаптером `site_protocol.py`:

```json
{
  "protocol_version": 1,
  "jobs": [{
    "job_id": "print-job-uuid",
    "operation": "submit",
    "payload_hash": "sha256-of-normalized-payload",
    "payload": {
      "type": "shift_report",
      "report_id": "start-shift-42-final-v1",
      "shift_id": "42",
      "date": "2026-09-25",
      "preliminary": false,
      "revision": 1,
      "as_of": "2026-09-25T16:00:00.000Z",
      "source": "Итог кассы: кафе + прокат",
      "total": "80000.00",
      "transfers": [{"recipient": "Тестовый сотрудник", "amount": "3500.00"}]
    }
  }]
}
```

Суммы выше только пример. Расчёты сайта остаются в целых копейках. На границе агента
деньги передаются строкой рублей с двумя десятичными знаками, которую он уже понимает
через `Decimal`. Нельзя передать `8000000` копеек в поле `total` как рубли.
Для хеша применяется общий канонический формат JSON: отсортированные ключи,
UTF-8, без пробелов, суммы-строки, количества — целые числа; одинаковость формата
обязательно проверяется общими тестовыми примерами Node/Python.

Pi сначала в одной локальной транзакции сохраняет документ, связь с `job_id` сайта
и исходящее подтверждение. Только после фиксации подтверждает `received`.
Потеря ответа вызывает повтор доставки того же документа, а не новый `submit` с новым ID.

## 3. Подтверждения и статусы

`POST /api/print-agent/v1/events` принимает пачку событий:

```json
{
  "events": [{
    "event_id": "persistent-event-uuid",
    "job_id": "print-job-uuid",
    "attempt_id": "persistent-attempt-uuid",
    "sequence": 1,
    "status": "received",
    "payload_hash": "sha256-of-normalized-payload",
    "occurred_at": "2026-09-25T19:00:00+03:00",
    "cups_id": null
  }]
}
```

Ответ содержит `accepted_event_ids`. Агент хранит исходящие события до этого ответа
и безопасно повторяет их. Сайт дедуплицирует события, проверяет устройство/задание/хеш
и не откатывает статус из-за позднего старого события. Состояние каждой попытки хранится отдельно.
Переход фазы/статуса агента и запись исходящего события выполняются атомарно в его SQLite.

| Состояние | Смысл и отображение в админке |
|---|---|
| `queued` на сайте | «В очереди», при отсутствии связи — «Ожидает связи с принтером» |
| `received` | «Получено агентом»: сохранено на Pi, это ещё не печать |
| `printing` | «Передаётся на печать», с ID CUPS |
| `printed` | «CUPS завершил задание»; не обещание физического выхода бумаги |
| `failed` | «Ошибка»; при неоднозначной передаче — «Нужна проверка принтера», без автоповтора |
| `cancelled` на сайте | Снято до первого предложения агенту; локальная печать не запускается |

`POST /api/print-agent/v1/heartbeat` передаёт состояние CUPS, готовность очереди,
`printing_enabled`, число ожидающих заданий и версию протокола. Сайт сохраняет время
последней связи; offline не означает failed и не разрешает повторную печать.

Переполненная очередь — временная ошибка `QUEUE_FULL`, HTTP 503; не удалять задание
с сайта и не создавать новый ID. Конфликт ID/содержимого — отдельная постоянная ошибка,
которая требует разбора и не блокирует получение остальных исправных документов.

## 4. Защита от дубликатов и повторная печать

- Для кафе ключ привязан к событию `cafe_order_events.id`: новый заказ и дозаказ имеют разные документы.
- Для отчёта ключ привязан к `shift_id` и редакции снимка. Двойное нажатие, две вкладки,
  повтор POST после обрыва и перезапуск возвращают существующее задание. Ограничение
  UNIQUE и транзакция на сервере обязательны; блокировки кнопки недостаточно.
- Обычная кнопка не создаёт новую редакцию при изменившихся финансовых данных.
  Показывается сохранённый отчёт и предложение явно сформировать новую редакцию.
- «Повторная печать» — отдельное действие администратора с подтверждением и причиной.
  Сервер выдаёт новый постоянный `job_id` для команды `operation: "reprint"`, агент запоминает результат команды в БД.
  Повтор доставки команды возвращает прежнюю попытку даже после её завершения.
- Ручной повтор печатает прежний снимок с пометкой **ПОВТОР**. Новая редакция имеет
  отдельный номер и пометку **НОВАЯ РЕДАКЦИЯ**, прежний снимок сохраняется.
- Неопределённый исход, потерянная история CUPS, активное/удержанное старое задание
  требуют проверки. Повтор не отменяет старое задание и не обходит проверку CUPS автоматически.
- Журнал сайта хранит автора, время, источник, редакцию, причину повтора и все статусы.
- Гарантируется дедупликация заданий и запрет автоматической повторной отправки при
  неоднозначном исходе; обещать ровно один физический лист при любых сбоях нельзя.

## 5. Отчёт смены и источники финансовых данных

По умолчанию выбирается текущая кассовая смена, а после закрытия — последняя.
Открытая смена печатается с пометкой **ПРЕДВАРИТЕЛЬНЫЙ ОТЧЁТ** по существующему
текущему расчёту проката и кафе. Закрытая — **ИТОГОВЫЙ ОТЧЁТ** по сохранённой кассе.
Эти два состояния имеют разные ключи документов; промежуточный отчёт не блокирует итоговый.
Кнопка размещается в существующих разделах «Смена и касса» и истории смен/зарплат,
доступна роли `admin`. Одна серверная функция, без параллельных расчётов во frontend.
Кнопка не закрывает смену, не отмечает зарплаты выплаченными и не переводит деньги.

Источник общего итога: `shifts.total_revenue_cents`. Он уже рассчитан как:

`касса на конец − касса на начало + изъятия директора + безнал`.

**Подтверждено владельцем: итог кассы — кафе + прокат.** В отчёт берётся сохранённый
общий итог закрытой смены. Добавлять к нему сумму кафе повторно нельзя.
Отдельные суммы прочих услуг не предполагаются и к итогу автоматически не прибавляются.

Источники расшифровки сейчас неодинаковы:

- Прокат: журнал `payments`, дата оплаты по Москве; есть корректировки оплат.
- Кафе: сумма заказов `DELIVERED` по дате выдачи; поле способа оплаты отражает выбор,
  отдельного журнала фактического приёма оплаты/возвратов кафе в коде нет.
- Прочие услуги: отдельного платёжного журнала услуг в текущем коде не найдено.

Поэтому не выдавать такую расшифровку за точно сверенные оплаты и не объявлять разницу
между кассой и прокатом/кафе «прочими услугами». Если требуется отдельная точная сумма
по каждому направлению, сперва требуется источник учёта оплат этих направлений.

**Подтверждено владельцем:** «Кому сколько перевести» только за текущую смену,
если она закрылась — за последнюю. Старые долги не включаются. Остаток:
`shift_employees.salary_cents − SUM(payroll_payments.amount_cents)` для этого сотрудника
и этой смены, на момент формирования снимка. Уже выплаченное вычитается. Нулевые остатки
не включаются; если все оплачены — «Переводов нет». Имя берётся из существующего профиля.
Старые долги не подмешиваются в сумму за выбранную смену. Формулу зарплаты не менять.

Снимок фиксирует ID смены, дату, время формирования, исходный итог кассы,
начислено/оплачено/остаток по людям, общий остаток к выплате, автора и редакцию.
Повторная печать не пересчитывает этот снимок задним числом.

## 6. Заказы кафе

- После сохранения нового заказа/дозаказа создаётся задание в той же транзакции.
  Для дозаказа печатаются только новые позиции с явной подписью «ДОЗАКАЗ».
- Используются сохранённые названия, количества, варианты, добавки, комментарии,
  номер заказа, место получения и суммы; телефон и токен публичного доступа не нужны.
- `pickup/lounge/yacht/place` сайта преобразуются в понятные русские подписи,
  поскольку текущий агент знает только `lounge/takeaway/delivery`.
- Отмена должна иметь отдельное уведомление с пометкой «ОТМЕНА», если заказ уже
  передан агенту. Если заказ ещё точно не выдавался агенту, его можно снять с очереди
  в серверной транзакции. Не молча изменять ранее отправленный снимок.
- Автопечать начинается с момента включения интеграции. Исторические заказы не
  подхватываются массово. Повторная печать доступна только для уже сохранённого документа.

## 7. Порядок реализации и проверки

1. Добавить серверную очередь, защищённый API агента и тесты дедупликации.
2. Добавить адаптер подтверждений/статусов и ID команд повторной печати в существующий агент.
3. Связать кафе и отчёт с существующими сущностями; добавить кнопку, состояние связи и журнал.
4. Проверить потерянный ACK, повтор POST, параллельные нажатия, перезапуск обеих сторон,
   обрыв во время CUPS, неактуальные статусы, переполненную очередь, несовпадение payload,
   несовпадение БД устройства, ручной повтор и денежные единицы.
5. Настроить токен и polling при выключенной физической печати. Проверить на тестовом
   задании полный путь до подтверждённого сохранения на Pi и статусов в админке.
6. После доставки принтера отдельно проверить бумагу, кириллицу, 80 мм, отрезку и звук.
   Только затем включить физическую печать, предварительно проверив старую очередь.

Фактическое состояние установки и результаты проверок фиксируются в PRINT-INTEGRATION.md.
